# قاموس حقول دمج النواة المحاسبية في مشروع مبيعات آخر

> **الإصدار:** 1.0 — قاموس تنفيذي أولي  
> **تاريخ الاستخراج:** 2026-09-14  
> **المصدر:** البنية الفعلية لقاعدة `CPOS_ACCOUNTING` وإجراءات مشروع CPOS  
> **نموذج النشر:** قاعدة بيانات واحدة تحتوي على جداول مشروع المبيعات والنواة المحاسبية  
> **القرار المعتمد:** تضاف حقول الربط مباشرة إلى جداول المطور، ولا تنسخ جداول مبيعات CPOS إلى مشروعه.

---

## 1. الغرض وحدود هذه المرحلة

يحدد هذا الملف الحقول المحاسبية التي يحتاج المطور إلى إضافتها إلى جداوله الموجودة، وأنواعها، ومكانها، والغرض منها. كما يحدد الجداول التي تنقل كاملة مع النواة المحاسبية ولا تدمج حقولها يدويا في جداول المبيعات.

هذا الملف قابل للتسليم قبل استلام مخطط مشروع المطور، لكنه لا يصبح ملف ترقية نهائيا قابلا للتنفيذ إلا بعد استبدال أسماء الجداول والمفاتيح بالأسماء الفعلية في مشروعه.

القواعد الأساسية:

- لا يطلب من المطور إعادة تسمية جداوله لتصبح مثل CPOS.
- لا يطلب منه نسخ `Agents` أو `Agents_Balance_MV` أو `SB_Contents`.
- يضاف رابط الحساب مباشرة إلى جدول كل كيان مالي.
- تضاف دورة حياة القيد إلى رأس كل معاملة قابلة للترحيل.
- لا تضاف أرصدة دفتر الأستاذ إلى جداول العملاء أو المخازن.
- القيم المالية الجديدة تستخدم `NUMERIC(18,3)`، ولا تستخدم `FLOAT`.
- التاريخ المتوافق مع البنية الحالية هو `DATETIME`.
- كود الحساب المتوافق مع `ACCOUNTS_TREE.ACC_CODE` هو `VARCHAR(40)`.

---

## 2. اصطلاحات الأسماء

هذه الأسماء هي العقد القياسي للحزمة. يستطيع المطور الاحتفاظ بأسماء حقوله، لكن ملف المواءمة يجب أن يبين المقابل بصورة صريحة.

| الاسم القياسي | الاسم التاريخي في CPOS | المعنى |
|---|---|---|
| `AccountingAccountCode` | `Tree_Code` أو `TREE_CODE` | كود حساب الكيان في دليل الحسابات |
| `AccountingLinkId` | `ACC_LINK_ID` | معرف سجل الربط والمزامنة المحاسبية |
| `JournalId` | `JournalId` | القيد الحالي المرتبط بالمعاملة |
| `PostedAt` | `PostedAt` | وقت آخر ترحيل ناجح |
| `PostedBy` | `PostedBy` | المستخدم الذي رحل الحركة |
| `OriginalJournalId` | `OriginalJournalId` | أول قيد قبل إعادة التقييد |
| `LastReversalJournalId` | `LastReversalJournalId` | آخر قيد عكسي ناتج عن تعديل |
| `NeedRepost` | `NeedRepost` | المعاملة عدلت وتحتاج إعادة تقييد |
| `EditVersion` | `EditVersion` | رقم نسخة التعديل المحاسبي |
| `VoidReversalJournalId` | `VoidReversalJournalId` | قيد عكس الإلغاء |
| `NeedCancelReverse` | `NeedCancelReverse` | الإلغاء يحتاج قيدا عكسيا |
| `SourceKey` | إضافة محمولة جديدة | مفتاح نصي ثابت يدعم مفاتيح `INT/BIGINT/GUID` في مشروع المطور |

عند إنشاء طبقة التوافق مع الإجراءات الحالية، يمكن للمطور:

1. استخدام أسماء CPOS نفسها؛ أو
2. استخدام الأسماء القياسية وإنشاء View/Adapter يعرض أسماء CPOS المطلوبة.

## 3. الحقول المشتركة لربط الكيانات بالدليل

### 3.1 المجموعة `ENTITY_ACCOUNT_LINK_FIELDS`

تضاف هذه الحقول إلى جدول كل كيان يحتاج حسابا مستقلا في الأستاذ العام:

| الحقل القياسي | نوع SQL | Null | الافتراضي | المرجع | الغرض |
|---|---|---|---|---|---|
| `AccountingAccountCode` | `VARCHAR(40)` | نعم أثناء الترحيل | لا يوجد | `ACCOUNTS_TREE.ACC_CODE` | حساب الكيان في الدليل |
| `AccountingLinkId` | `INT` | نعم | لا يوجد | `ACC_ENTITY_LINKS.LINK_ID` | معرف الربط المستخدم للمزامنة والتدقيق |

في مشروع يحافظ على توافق أسماء CPOS مباشرة، تستخدم:

```sql
Tree_Code  VARCHAR(40) NULL,
ACC_LINK_ID INT NULL
```

### 3.2 الجداول التي تحصل على المجموعة

| جدول المطور المنطقي | نوع الكيان | حساب الأب الذي يحدد من الإعدادات | المقابل الحالي في CPOS |
|---|---|---|---|
| العملاء | عميل | رقابة العملاء | `Agents` عندما يكون عميلًا |
| الموردون | مورد | رقابة الموردين | `Agents` عندما يكون موردًا |
| الموظفون | موظف | ذمم الموظفين/المستحقات | `Agents` عندما يكون موظفًا |
| الخزائن | خزينة نقدية | النقدية بالصندوق | `TreasuryCard` |
| الحسابات البنكية | مصرف | النقدية لدى المصارف | `TreasuryCard` مع `is_BANK=1` |
| المخازن | مخزن | المخزون | `Stores` |
| بطاقات المصروف العام | مصروف | مجموعة المصروفات المناسبة | `Expenses_Card` |
| بطاقات مصروف المشتريات | مصروف شراء | المصروف أو تحميل التكلفة | `Pch_Exp_Card` |

### 3.3 الفروق الفعلية في CPOS

| الجدول الحالي | حقل الحساب | نوعه | حقل الربط | نوعه |
|---|---|---|---|---|
| `Agents` | `Tree_Code` | `VARCHAR(50) NULL` | `ACC_LINK_ID` | `INT NULL` |
| `Stores` | `TREE_CODE` | `VARCHAR(40) NULL` | `ACC_LINK_ID` | `INT NULL` |
| `TreasuryCard` | `Tree_Code` | `VARCHAR(40) NULL` | `ACC_LINK_ID` | `INT NULL` |
| `Expenses_Card` | `Tree_Code` | `VARCHAR(40) NULL` | `ACC_LINK_ID` | `INT NULL` |
| `Pch_Exp_Card` | `Tree_Code` | `VARCHAR(40) NULL` | `ACC_LINK_ID` | `INT NULL` |

يوصى في المشروع الجديد بتوحيد كود الحساب على `VARCHAR(40)` لأنه يطابق المفتاح الفريد الفعلي `ACCOUNTS_TREE.ACC_CODE`. اتساع حقل العميل إلى 50 في CPOS توافق تاريخي وليس حاجة للنواة.

### 3.4 القيود والفهارس المطلوبة

بعد تعبئة وربط البيانات القديمة:

- مفتاح خارجي من `AccountingAccountCode` إلى `ACCOUNTS_TREE.ACC_CODE`.
- مفتاح خارجي من `AccountingLinkId` إلى `ACC_ENTITY_LINKS.LINK_ID` إذا احتفظت النواة بجدول الروابط.
- فهرس غير فريد على `AccountingAccountCode` في كل جدول كيان.
- يفضل قيد فريد مفلتر على كود الحساب لكل نوع كيان إذا كانت السياسة تمنع مشاركة الحساب.
- لا تجعل الحقل `NOT NULL` للكيانات التي لا تشارك محاسبيا.
- تمنع إجراءات الترحيل الحركة المالية عندما يكون حساب الكيان الإلزامي فارغا.

مثال عام غير قابل للتنفيذ قبل استبدال الاسم:

```sql
ALTER TABLE dbo.[<CustomerTable>]
ADD Tree_Code   VARCHAR(40) NULL,
    ACC_LINK_ID INT NULL;

CREATE INDEX IX_<CustomerTable>_Tree_Code
ON dbo.[<CustomerTable>](Tree_Code);

ALTER TABLE dbo.[<CustomerTable>] WITH CHECK
ADD CONSTRAINT FK_<CustomerTable>_Tree_Code
FOREIGN KEY (Tree_Code) REFERENCES dbo.ACCOUNTS_TREE(ACC_CODE);
```

## 4. الحقول المشتركة لدورة حياة المعاملة المحاسبية

### 4.1 المجموعة `ACCOUNTING_POSTING_LIFECYCLE_FIELDS`

تضاف إلى رأس كل معاملة يمكن أن تنتج قيدا مستقلا:

| الحقل | نوع SQL | Null | الافتراضي | الغرض |
|---|---|---|---|---|
| `JournalId` | `INT` | نعم | لا يوجد | القيد الحالي للمعاملة |
| `PostedAt` | `DATETIME` | نعم | لا يوجد | تاريخ ووقت آخر ترحيل |
| `PostedBy` | `INT` | نعم | لا يوجد | المستخدم المرحّل |
| `OriginalJournalId` | `INT` | نعم | لا يوجد | القيد الأصلي قبل التعديل |
| `LastReversalJournalId` | `INT` | نعم | لا يوجد | آخر قيد عكسي بسبب إعادة التقييد |
| `NeedRepost` | `BIT` | لا | `0` | المعاملة تحتاج عكس القيد وإعادة إنشائه |
| `EditVersion` | `INT` | لا | `0` | عدد دورات التعديل المحاسبي |
| `EditOpenedAt` | `DATETIME` | نعم | لا يوجد | وقت فتح المعاملة للتعديل |
| `EditOpenedBy` | `INT` | نعم | لا يوجد | المستخدم الذي فتح التعديل |
| `LastRepostAt` | `DATETIME` | نعم | لا يوجد | وقت آخر إعادة تقييد |
| `LastRepostBy` | `INT` | نعم | لا يوجد | منفذ آخر إعادة تقييد |
| `VoidAt` | `DATETIME` | نعم | لا يوجد | وقت الإلغاء |
| `VoidBy` | `INT` | نعم | لا يوجد | منفذ الإلغاء |
| `VoidReason` | `NVARCHAR(500)` | نعم | لا يوجد | سبب الإلغاء |
| `VoidReversalJournalId` | `INT` | نعم | لا يوجد | قيد عكس الإلغاء |
| `NeedCancelReverse` | `BIT` | لا | `0` | الإلغاء ما زال يحتاج قيدا عكسيا |

هذه المواصفات مطابقة للحقول الموجودة فعليا في `Agents_Balance_MV` و`Agents_Balance_MV_RCT` و`Treasury_Balance_MV` و`AG_MV_TRANSACTION`.

داخل قيد اليومية المحمول تخزن هوية المصدر في `SourceTable SYSNAME` و`SourceKey NVARCHAR(100)`، مع `SourceId BIGINT NULL` للفهرسة عندما يكون مفتاح مشروع المطور رقميا. `SourceKey` هو المرجع الإلزامي لمنع تكرار القيد، لأنه يستوعب أيضا المفاتيح من نوع `UNIQUEIDENTIFIER` من دون فرض نوع مفتاح موحد على مشروع المطور.

### 4.2 أين تضاف المجموعة؟

| رأس معاملة المطور | المجموعة | ملاحظات |
|---|---|---|
| فاتورة البيع | كاملة | قيد الإيراد والتكلفة |
| مرتجع البيع | كاملة | قيد عكس البيع وإعادة المخزون |
| فاتورة الشراء | كاملة | قيد المورد والمشتريات/المخزون |
| مرتجع الشراء | كاملة | عكس الأثر حسب السياسة |
| سند القبض | كاملة | تسوية العميل مقابل الخزينة |
| سند الصرف | كاملة | تسوية المورد/العميل مقابل الخزينة |
| المصروف | كاملة | المصروف مقابل الخزينة أو الدائن |
| حركة التلف | كاملة | مصروف التلف مقابل المخزون |
| تسوية المخزون | كاملة | ربح/خسارة التسوية مقابل المخزون |
| تحويل بين الحسابات | كاملة بعد دعم مسار العكس | يجب استكمال `REPOST/CANCEL_REVERSE` |
| تحويل بين الخزائن | كاملة بعد دعم مسار العكس | يجب استكمال `REPOST/CANCEL_REVERSE` |
| تحويل مخزني | كاملة إذا نتج عنه قيد | يتحدد حسب سياسة حساب المخازن |
| الرصيد الافتتاحي | كاملة | يمنع تعديله بعد الإقفال دون صلاحية |

لا تضاف المجموعة إلى جدول تفاصيل الأصناف؛ السطر لا يملك قيدا مستقلا عن رأس المستند في التصميم الحالي.

### 4.3 قالب الإضافة

```sql
ALTER TABLE dbo.[<TransactionHeaderTable>]
ADD JournalId                INT NULL,
    PostedAt                 DATETIME NULL,
    PostedBy                 INT NULL,
    OriginalJournalId        INT NULL,
    LastReversalJournalId    INT NULL,
    NeedRepost               BIT NOT NULL
        CONSTRAINT DF_<Table>_NeedRepost DEFAULT (0),
    EditVersion              INT NOT NULL
        CONSTRAINT DF_<Table>_EditVersion DEFAULT (0),
    EditOpenedAt             DATETIME NULL,
    EditOpenedBy             INT NULL,
    LastRepostAt             DATETIME NULL,
    LastRepostBy             INT NULL,
    VoidAt                   DATETIME NULL,
    VoidBy                   INT NULL,
    VoidReason               NVARCHAR(500) NULL,
    VoidReversalJournalId    INT NULL,
    NeedCancelReverse        BIT NOT NULL
        CONSTRAINT DF_<Table>_NeedCancelReverse DEFAULT (0);
```

بعد نقل النواة تضاف مفاتيح `JournalId`, `OriginalJournalId`, `LastReversalJournalId`, `VoidReversalJournalId` إلى `ACC_BALANCE_MASTER.T_ID` عندما لا تمنع بيانات تاريخية غير سليمة ذلك. مشروع CPOS الحالي لا يفرض كل هذه المفاتيح فعليا، ولذلك يجب فحص البيانات قبل تشديد القيود في المشروع الجديد.

### 4.4 الفهارس المقترحة للمراقبة

```sql
CREATE INDEX IX_<Table>_AccountingPostingStatus
ON dbo.[<TransactionHeaderTable>]
(
    NeedRepost,
    NeedCancelReverse,
    JournalId
);
```

يضاف `IsVoid` إلى مفتاح الفهرس إذا كان اسم حقل الإلغاء في جدول المطور مختلفا أو كانت استعلامات المراقبة تستخدمه بكثافة.

## 5. الحقول التشغيلية التي يجب أن تتوافر للفاتورة

هذه الحقول لا يلزم إضافتها إذا كان لها مقابل موثوق في مشروع المطور. المطلوب هو توثيق المقابل وتحويله إلى العقد الموحد.

### 5.1 رأس الفاتورة أو المرتجع

| القيمة الدلالية | النوع القياسي | إلزامية | ملاحظات |
|---|---|---|---|
| `DocumentId` | نوع مفتاح جدول المطور | نعم | المعرف الداخلي الثابت |
| `DocumentNumber` | `NVARCHAR(50)` | نعم | رقم عرض/بحث، وليس مفتاح منع التكرار وحده |
| `DocumentType` | `INT` | نعم | يربط بخريطة نوع الحركة |
| `DocumentDate` | `DATETIME` | نعم | تاريخ المستند والترحيل حسب سياسة الفترة |
| `PartyId` | نوع مفتاح العميل/المورد | نعم | العميل أو المورد |
| `GrossTotal` | `NUMERIC(18,3)` | نعم | الإجمالي قبل خصم الرأس |
| `DiscountAmount` | `NUMERIC(18,3)` | لا | افتراضيا صفر |
| `TaxAmount` | `NUMERIC(18,3)` | لا | عند تطبيق الضرائب |
| `RoundingAmount` | `NUMERIC(18,3)` | لا | فروق التقريب الصريحة |
| `NetAmount` | `NUMERIC(18,3)` | نعم | يعاد احتسابه والتحقق منه بالخادم |
| `PaidAmount` | `NUMERIC(18,3)` | لا | يطابق صافي الإيصالات الفعالة |
| `CurrencyId` | `INT` | نعم عند التفعيل | CPOS يستخدم `Cr_ID`/`Currency_ID` |
| `ExchangeRate` | `NUMERIC(18,3)` | نعم عند التفعيل | لا يقبل صفرا |
| `CostCenterId` | `INT` | حسب السياسة | مرجع `COST_CENTER.COST_ID` |
| `UserId` | `INT` | نعم | المنفذ التشغيلي |
| `IsApproved` | `BIT` أو خريطة من حالة المطور | نعم | لا يرحل غير المعتمد |
| `IsVoid` | `BIT` مفضل | نعم | الملغي لا يرحل كحركة فعالة |
| `OriginalDocumentId` | نوع مفتاح المستند | للمرتجع | يربط المستند العكسي بالأصل |

### 5.2 تفاصيل الأصناف

| القيمة الدلالية | النوع القياسي | إلزامية | الغرض المحاسبي |
|---|---|---|---|
| `LineId` | نوع مفتاح التفاصيل | نعم | تتبع السطر |
| `DocumentId` | نوع مفتاح الرأس | نعم | الربط بالرأس |
| `ItemId` | نوع مفتاح الصنف | نعم | الصنف |
| `UnitId` | نوع مفتاح الوحدة | نعم | تحويل الكمية |
| `StoreId` | نوع مفتاح المخزن | نعم للمخزون | تحديد حساب المخزن |
| `Quantity` | `NUMERIC(18,3)` | نعم | الكمية المباعة/المرتجعة |
| `UnitPrice` | `NUMERIC(18,3)` | نعم | سعر الوحدة |
| `LineDiscount` | `NUMERIC(18,3)` | لا | خصم السطر |
| `LineTax` | `NUMERIC(18,3)` | لا | ضريبة السطر |
| `LineNet` | `NUMERIC(18,3)` | نعم | صافي السطر |
| `UnitCost` | `NUMERIC(18,3)` | نعم لقيد التكلفة | لا يستخدم `FLOAT` في العقد الجديد |
| `CostCenterId` | `INT` | حسب السياسة | يسمح بتخصيص السطر |

## 6. حقول الدفع والإيصالات والخزائن

### 6.1 عقد سطر الدفع

المواصفات المطابقة لـ`SalePaymentAllocationType`:

| الحقل | نوع SQL | Null | القاعدة |
|---|---|---|---|
| `LineNo` | `INT` | لا | مفتاح السطر داخل الطلب |
| `PaymentMethodID` | `INT` | لا | طريقة دفع فعالة |
| `TreasuryID` | `INT` | لا | خزينة أو مصرف موجود |
| `Amount` | `DECIMAL(18,3)` | لا | أكبر من صفر |
| `ReferenceNumber` | `NVARCHAR(100)` | نعم | مرجع التحويل/البطاقة |
| `BankName` | `NVARCHAR(150)` | نعم | اسم المصرف عند الحاجة |
| `CheckNumber` | `NVARCHAR(100)` | نعم | رقم الشيك |

| `PartyId` | نوع مفتاح العميل/المورد | نعم |

| `TreasuryId` | نوع مفتاح الخزينة | نعم |
| `ReceiptDate` | `DATETIME` | نعم |

### 6.3 إعداد طريقة الدفع

تنقل بنية مكافئة لـ`PaymentMethodDefaultAccounts` لأن طريقة الدفع قد تحتاج خزينة محددة أو مقفلة:

| الحقل الحالي | نوع SQL | Null | الافتراضي |
|---|---|---|---|
| `ID` | `INT` | لا | مفتاح أساسي |

| `AccountID` | `INT` | لا | يمثل الخزينة في السلوك الحالي |
| `Notes` | `NVARCHAR(250)` | نعم | لا يوجد |
| `IsActive` | `BIT` | لا | `1` |
| `Percent_Disc` | `NUMERIC(18,3)` | نعم | حسب السياسة |
| `is_Lock` | `BIT` | نعم | حسب السياسة |

ينبغي في النسخة المحمولة إعادة تسمية `AccountID` إلى `TreasuryId` لتجنب اعتباره حساب أستاذ عام، أو توفير View توافقية إذا بقيت الإجراءات الحالية دون تعديل.

## 7. المصروفات والمشتريات والمخزون

### 7.1 بطاقة المصروف

يضاف إليها `ENTITY_ACCOUNT_LINK_FIELDS`. أما حركة المصروف فتحتفظ بقيمة المصروف والخزينة/الدائن والتاريخ ومركز التكلفة، وتحصل على `ACCOUNTING_POSTING_LIFECYCLE_FIELDS`.

لا يكفي ربط كل المصروفات بحساب عام واحد إذا كانت قائمة الدخل تحتاج تحليلا حسب النوع. يجب أن يكون حساب بطاقة المصروف حساب حركة صالحا، أو توجد قاعدة صريحة تربطه بالحساب النظامي العام.

### 7.2 المخزن

يضاف إلى جدول المخزن:

```sql
Tree_Code   VARCHAR(40) NULL,
ACC_LINK_ID INT NULL
```

الحقل `Tree_Code` يمثل حساب قيمة المخزون، وليس حساب تكلفة البضاعة. حساب `COGS` يأتي من الحسابات النظامية أو من تخصيص مجموعة الصنف إذا أضيف ذلك لاحقا.

### 7.3 الصنف أو مجموعة الصنف

النواة الحالية تستطيع الترحيل باستخدام حسابات نظامية وحساب المخزن. إذا كان مشروع المطور يحتاج حسابات مختلفة حسب مجموعة الصنف، يمكن دعم الحقول التالية كمرحلة اختيارية:

| الحقل | النوع | الغرض |
|---|---|---|
| `SalesAccountCode` | `VARCHAR(40) NULL` | حساب إيراد مخصص |
| `SalesReturnAccountCode` | `VARCHAR(40) NULL` | مردودات مبيعات مخصصة |
| `COGSAccountCode` | `VARCHAR(40) NULL` | تكلفة مخصصة |
| `InventoryAccountCode` | `VARCHAR(40) NULL` | مخزون مخصص |

لا تفعل هذه الحقول إلا بعد تحديد أولوية واضحة: حساب الصنف، ثم المجموعة، ثم الحساب النظامي. غياب قاعدة الأولوية يؤدي إلى اختلاف القيود بين الفواتير.

### 7.4 الشراء ومصروفاته

- المورد يحصل على رابط حساب كيان.
- رأس فاتورة الشراء يحصل على دورة حياة القيد.
- تفاصيل الشراء توفر المخزن والكمية والتكلفة والضرائب والمصروفات المحملة.
- بطاقة مصروف الشراء تحصل على رابط حساب.
- يحدد لكل مصروف شراء هل يحمل على المخزون أم يذهب مباشرة إلى قائمة الدخل.

## 10. ترتيب إضافة الحقول إلى مشروع قائم

يطبق التغيير على مراحل، ولا تحول الحقول إلى إلزامية مباشرة على جدول يحتوي بيانات قديمة:

1. أخذ نسخة احتياطية قابلة للاستعادة.
2. تثبيت النواة المحاسبية الأساسية.
3. إضافة حقول ربط الكيانات كـ`NULL`.
4. إنشاء الحسابات الأب والحسابات النظامية.
5. إنشاء/ربط حساب لكل عميل ومورد وخزينة ومصرف ومخزن ومصروف مطلوب.
6. التحقق من عدم وجود أكواد حسابات مكررة أو مفقودة.
7. إضافة حقول دورة الحياة إلى رؤوس المعاملات، مع القيم الافتراضية فقط للأعلام.
8. ترحيل أو تحديد حالة المستندات التاريخية: غير مقيدة، مقيدة سابقا، أو خارج نطاق البداية.
9. إنشاء الفهارس.
10. إضافة المفاتيح الخارجية باستخدام `WITH CHECK` بعد تنظيف البيانات.
11. تشديد `NOT NULL` فقط للكيانات التي تفرض السياسة ربطها.
12. تشغيل اختبار ميزان المراجعة والمطابقة قبل فتح الترحيل للمستخدمين.

## 12. ضوابط قبول الحقول

قبل اعتبار إضافة الحقول ناجحة يجب إثبات:

- كل كود حساب مضاف موجود في `ACCOUNTS_TREE`.
- حساب الكيان حساب حركة غير مقفل عندما تتطلب القاعدة ذلك.
- لا توجد فاتورة تشير إلى عميل بلا حساب عندما يكون الربط إلزاميا.
- لا يوجد سطر مخزون بلا مخزن مرتبط بحساب.
- لا توجد طريقة دفع مفعلة دون خزينة صالحة.
- كل `JournalId` موجود يشير إلى قيد حقيقي.
- `NeedRepost=1` لا يستخدم لمعاملة لم تقيد أصلا إلا كحالة خطأ ظاهرة.
- المعاملة الملغية التي لها قيد أصلي إما لها `NeedCancelReverse=1` أو `VoidReversalJournalId`.
- الفهارس لا تحتوي أسماء مكررة مع فهارس مشروع المطور.
- ملفات الترقية قابلة لإعادة التشغيل بأمان أو تتوقف برسالة واضحة دون تنفيذ جزئي.

## 13. ما لم يحسم بعد

تحتاج البنود التالية إلى مخطط مشروع المطور أو قرار محاسبي قبل إنشاء SQL النهائي:

- أسماء جداول ومفاتيح العملاء والموردين والموظفين.
- هل العميل والمورد في جدول واحد أم جداول منفصلة.
- أسماء جداول الفواتير والمرتجعات والسندات والتفاصيل.
- نوع مفاتيح الجداول: `INT` أو `BIGINT` أو `UNIQUEIDENTIFIER`.
- مكان تكلفة الصنف وطريقة احتسابها تاريخيا.
- هل ربط المخزون على مستوى المخزن أم مجموعة الصنف أم الاثنين.
- هل المصروف يدفع مباشرة أم يسجل على دائن ثم يسوى.
- الضرائب والعملات ومراكز التكلفة والفروع الداخلة في المرحلة الأولى.
- سياسة ترحيل المستندات التاريخية.
- إصدار SQL Server المستهدف؛ القوالب الأساسية ستبقى متوافقة مع SQL Server 2014 ما لم يقرر غير ذلك.

هذه البنود لا تمنع استكمال استخراج النواة المحاسبية، لكنها تمنع إصدار ملف `ALTER TABLE` نهائي بأسماء مشروع المطور قبل استلام مخططه.
