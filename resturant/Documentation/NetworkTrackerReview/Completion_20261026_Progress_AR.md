# استكمال الانتقال الشامل — نقطة تحقق 020 والسجل الإداري المحلي

التاريخ: 2026-10-26. هذه **نقطة تقدم وليست إعلان اكتمال التعميم**. التكليف المعتمد هو مواصلة جميع المسارات دون طلب موافقة لكل دفعة، مع استثناء المسودات وOffline، وعدم استبدال نسخة التشغيل الأساسية.

## القرارات الجديدة المعتمدة

- طلب المستخدم إدراج مراقبة استعادة قاعدة البيانات، واختار **سجلًا محليًا مستقلًا على جهاز تنفيذ الاستعادة**، لا قاعدة إدارية منفصلة.
- اختار المستخدم نقل مراقبة الإلغاء **دون تصحيح إجراء الإلغاء التجاري**. لذلك لم نغيّر المستخدم الثابت `1` داخل `AG_Balance_Void_Row` وتوابعه، ولم نغيّر شرط إزالة مكونات البيع المرتبط باعتماد الرأس.
- هذه العيوب ليست ضمانًا بصحة الأثر التجاري؛ النظام الجديد يحفظ الحقيقة كما نفذها الإجراء، ولا يصنع نجاحًا محاسبيًا غير حاصل.

## الإلغاء الذري

أُضيف `Document.Voided` في المجال `Documents.Cancellation`، وربط `AuditDocumentVoidUi` في **17 شاشة / 18 اقتران شاشة ونوع / 12 نوع معاملة**:

- البيع: Sales، Sales_Fast، POS، OrdersMenu، POS_Abcent_Bills، ShowBill_IM.
- المصروفات EXP_Details، المشتريات Pch، التالف IM_Execute، الجرد Invoice.
- Returns لنوعي إرجاع المبيعات والمشتريات، وViewBill لعروض الأسعار (نوع 16).
- التصنيع الآلي واليدوي، صرف المخزون Inside_Sales، واستلامه Outside_Sales وOutside_Sales_Touch.

كل مسار يستعمل اتصالًا ومعاملة Serializable واحدة: حجز طلب ثابت → التحقق من المستخدم وصلاحية الشاشة → قفل وقراءة البيانات → مقارنة اللقطة السابقة → تنفيذ الإجراء الأصلي → قراءة النتيجة → كتابة الأحداث وتفاصيلها → إكمال الطلب → Commit. فشل التسجيل يلغي العملية. فقد الرد يُحسم بالطلب نفسه ولا يؤدي تلقائيًا إلى إلغاء ثانٍ.

التفاصيل تشمل 23 قيمة للرأس، وحالة سطور كل نوع وهوياتها ومقاديرها المخزنية، و20 قيمة لكل إيصال، وحركات الخزينة المرتبطة، ومكونات البيع الموجودة/المحذوفة، وأرصدة المخزون قبل/بعد، وحالة الطاولة. يُسجل عدد صفوف طابور طباعة الإلغاء قبل/بعد؛ هذا **ليس إثبات طباعة ورقية**. تُقسم التفاصيل إلى أجزاء دون اقتطاع، وتظل حدود الكاتب الحالية 100 حدث × 100 قيمة. تجاوزها يرفض المعاملة ولا يسقط بقية الأدلة.

إجراءات الأعمال لم تتغير. ملف `Database/Audit/018_Document_Cancellation.sql` يوسّع عقد المراقبة ويُفعّل المجال الثامن فقط. **طُبق على CPOS_ACCOUNTING** بعد الاختبارات. احتُفظ بتعريفات الإجراءات السابقة في `.tmp/AuditCancellation018/Before_*.xml`. لا تعاود تشغيل وضع Install أو Candidate على قاعدة مثبت عليها 018.

### قيود الإلغاء المعروفة

1. الحدث يسجل المستخدم الحقيقي، بينما حقل `VoidBy` التجاري يبقى `1` وفق الإجراء القديم. يظهر هذا الفرق صراحة في الرسالة والتفاصيل.
2. قبل اعتماد رأس البيع قد تبقى مكوناته؛ تُلتقط كصفوف موجودة، لا كصفوف محذوفة وهميًا.
3. إذا كان إيصال مرتبط ملغى سابقًا، قد يفشل الإجراء القديم عند إعادة إلغائه، وقد يظهر خطأ Rollback المتداخل. اختُبر رفض العملية والتراجع ولم يُصحح هذا السلوك ضمن نقل المراقبة.
4. إعداد علامة الحاجة لعكس القيد لا يعني إنشاء قيد عكسي فورًا. التقاط الحالة لا يغير آلية الربط المحاسبي.
5. لم تُجرَّب الواجهة تفاعليًا أو الطباعة الفعلية أو فصل الشبكة ماديًا؛ اختبارات الخدمة والقاعدة لا تستبدل ذلك.

## سجل استعادة القاعدة المحلي

الملف البرمجي: `Classes/Audit/AdministrativeRestoreAudit.vb`؛ المدخل: `Forms/Sys_Options/Backup.vb`.

المسار الافتراضي:

```text
%LOCALAPPDATA%\CPOS\AdministrativeAudit\Restore
```

هذا سجل **لكل حساب Windows على جهاز التنفيذ**، وليس سجلًا موحدًا لكل مستخدمي الأجهزة. لا يدخل داخل ملف bak، ولا داخل قاعدة CPOS_ACCOUNTING، ولا داخل مجلد تدوير النسخ الاحتياطية. لا توجد سياسة حذف تلقائي له. يجب نسخه احتياطيًا وحماية حساب Windows/القرص بصورة مستقلة. لا يظهر داخل شاشة أحداث قاعدة V2؛ ملفاته XML محلية قابلة للقراءة.

لكل محاولة مجلد GUID مستقل:

- `Started.xml`: هوية المستخدم/جلسة التطبيق والمصدر قبل الاستعادة، هوية Windows والجهاز، اسم السيرفر والقاعدة ومسار bak.
- `Dispatched.xml`: دليل حفظ نية إرسال الأمر، قبل الإرسال الفعلي. وجوده ليس إثبات نجاح التنفيذ.
- `Finished.xml`: `Succeeded` عند تأكيد SQL Server، أو `Unknown` إذا فشل الرد بعد الإرسال، أو `NotDispatched` إذا لم يُرسل الأمر.
- `Reviewed.xml`: قرار إداري صريح بالسماح بمحاولة جديدة بعد مراجعة الخادم؛ لا يبدل النتيجة السابقة ولا يزعم نجاحها.

تُكتب الملفات باستخدام CreateNew وFlush إلى القرص، ويمنع قفل الملف كاتبين متوازيين ضمن هذا المسار/الحساب. تُرفض الملفات التالفة ولا تُحذف. SHA-256 هنا لكشف التلف العرضي **وليس توقيعًا مقاومًا للعبث**؛ مالك حساب Windows أو مسؤول الجهاز يستطيع تعديل/حذف السجل، كما لا يحميه من ضياع القرص. الساعة المسجلة هي UTC جهاز التنفيذ مع وصف مصدرها، وليست ساعة SQL Server.

فشل حفظ بداية المحاولة يمنع إرسال الاستعادة. فشل حفظ النتيجة بعد نجاح SQL لا يُحوّل نجاح الاستعادة إلى فشل وهمي؛ يعرض نجاح SQL وتعذر تثبيت نتيجة المراقبة. عند الغموض لا توجد إعادة محاولة تلقائية. تظهر مراجعة إدارية قبل السماح بمحاولة جديدة.

لا تُحفظ سلسلة الاتصال أو كلمة المرور أو بصمتها أو رسالة الاستثناء الخام. رقم خطأ SQL فقط اختياري في سجل النتيجة. مسار bak قد يحتوي معلومات تشغيلية، لذلك تجب حماية ملفات السجل.

يُنفذ الأمر عبر اتصال `master` مستقل، واسم قاعدة مقتبس ومسار bak مُمرّر بمعامل. بقيت عملية SINGLE_USER ثم RESTORE WITH REPLACE كما كانت؛ لم تُضف سياسة إصلاح/إعادة MULTI_USER أو إعادة محاولة خفية. بعد إرسال الأمر تُبطل جلسة المراقبة القديمة دون الكتابة في القاعدة المستعادة، ويُطلب إعادة تشغيل التطبيق/الدخول بعد التأكد من جاهزية القاعدة. **لم ننفذ RESTORE حقيقيًا أثناء التطوير**؛ اختبارات هذا الجزء محاكاة محلية فقط.

## تعريف الوحدات — 019

تُلتقط حقول Units الفعلية كاملة: U_Name من nvarchar(250)، وU_Cargo من float(53) دون تقريب، وisDefault من bit. يبقى حد معامل الاسم في Unit_Insert/Unit_Update هو 100 حرف؛ يُسجل المخزن فعليًا، لا نص الواجهة المفترض. الحمولات الفارغة أو صفر تطبع إلى 1 كما سابقًا، ولم تُضف قاعدة منع الحمولات السالبة. يحمي المسار معرفي النظام 1 و2 من التعديل والحذف كما تفرض الواجهة، ويقفل نطاق الترقيم القائم دون تغيير خوارزميته.

القيم السابقة واللاحقة والحذف والإنشاء تحفظ مع العملية في معاملة Serializable، مع فحص المستخدم وصلاحية IM للشاشات التي تعتمدها أصلًا، وبصمة لكشف تغير الصف أثناء المحاولة. الإنشاء من النافذتين المساعدتين يحتفظ بسياسة مسار الأب الحالية دون اختراع صلاحية جديدة. إعادة الطلب نفسه تعيد المعرف الأصلي ولا تنشئ وحدة ثانية.
